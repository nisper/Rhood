# Page

Страница — верхнеуровневая интерфейсная сущность. Используй ее, когда пользователь просит собрать новый экран, переработать существующий экран или сделать вариант страницы по продуктовой задаче.

## Назначение

Страница должна помогать пользователю выполнить один основной сценарий или принять одно главное решение.

Перед сборкой страницы определи:

- кто пользователь страницы;
- какую задачу он решает;
- какое главное действие или решение есть на странице;
- какие данные нужны для этого действия;
- какие элементы обязательны, а какие вторичны.

Если задача не дает ответа на эти вопросы, сначала попробуй вывести их из контекста файла, названия экрана, соседних макетов и продуктовых материалов. Если вывод рискованный, спроси пользователя.

## Перед Сборкой

Перед созданием или перестройкой страницы обязательно проверь:

- есть ли в библиотеке базовый `Main Header` и нужные компоненты действий;
- есть ли готовые компоненты для ключевых сущностей страницы;
- есть ли подходящие text styles, color variables и semantic tokens;
- есть ли в файле похожая страница, которую нужно использовать как ориентир;
- какие элементы относятся к странице целиком, а какие к конкретному блоку.

Если для ключевой части страницы нет компонента, паттерна или понятного правила, не собирай ее как локальный placeholder. Сначала зафиксируй вопрос пользователю.

## Базовая структура

Продуктовая страница собирается из следующих блоков:

- `Main Header`;
- `Content`;
  - `Page Heading`;
  - `Page Body`.

`Main Header` — верхний компонент страницы из библиотеки.

`Content` — контейнер для содержимого конкретной страницы.

`Page Heading` задает контекст страницы.

`Page Body` содержит основной сценарий страницы: данные, формы, карты, списки, состояния и рабочие блоки.

## Main Header И Page Heading

Не смешивай `Main Header` и `Page Heading`.

`Main Header` — компонент из библиотеки, который относится к верхнему уровню страницы.

`Page Heading` — заголовочная зона конкретной страницы. Она задает контекст текущей страницы и должна быстро отвечать на вопрос: где находится пользователь и что здесь можно сделать.

В `Page Heading` обычно входят:

- название страницы;
- короткое описание, если без него смысл страницы неочевиден;
- главное действие страницы;
- вторичные действия, если они относятся ко всей странице.

Главное действие страницы размещай в `Page Heading` только если оно относится ко всей странице целиком. Если действие относится к конкретному блоку, строке, форме или состоянию, размещай его внутри соответствующей зоны.

## Основная Рабочая Область

Основная рабочая область должна занимать главный визуальный объем страницы.

В ней размещай:

- таблицу или список сущностей;
- форму;
- детали выбранной сущности;
- рабочий процесс;
- сводку с детализацией;
- пустое, ошибочное или ограниченное состояние, если данных нет.

Не смешивай в основной области несколько равнозначных сценариев без явного разделения. Если на странице есть несколько задач, сгруппируй их в отдельные смысловые блоки.

## Смысловые Блоки

Каждый блок на странице должен иметь одну функцию.

Блок может отвечать за:

- выбор режима или фильтра;
- просмотр данных;
- ввод данных;
- принятие решения;
- подтверждение действия;
- объяснение состояния.

Не объединяй в одном блоке элементы, которые нужны пользователю по разным причинам. Если элементы читаются в разное время сценария, скорее всего, это разные блоки.

## Правило Внутреннего И Внешнего

Внутренний отступ показывает, что элементы принадлежат одному блоку.

Внешний отступ показывает, что один блок закончился и начался другой.

Расстояние внутри смысловой группы должно быть меньше расстояния между разными группами. Визуальная близость должна совпадать со смысловой близостью.

Если структура плохо читается без рамок и фонов, сначала проверь отступы и группировку. Не добавляй контейнер только для украшения.

## Контейнеры

Контейнер нужен, если он помогает понять принадлежность элементов, ограничивает рабочую область или отделяет состояние от соседних блоков.

Не превращай каждый блок страницы в карточку. Часто достаточно вертикального layout, отступов, разделителей и системных компонентов.

Не вкладывай карточку в карточку без сильной причины.

## Управление Представлением

Фильтры, поиск, сортировка, табы и переключатели вида должны быть рядом с данными, на которые они влияют.

Если управление влияет на всю страницу, размещай его выше основной рабочей области.

Если управление влияет только на конкретный список, таблицу или блок, размещай его внутри этого блока.

Не меняй состав, порядок и смысл существующих фильтров или табов без явной задачи.

## Действия

На странице должен быть понятен приоритет действий:

- primary action — главное действие сценария;
- secondary actions — полезные, но не главные действия;
- destructive action — опасное действие, которое нужно отделять смыслом и визуально;
- row/item actions — действия над конкретной сущностью.

Не размещай действие в `Page Heading` только потому, что там есть место. Место действия определяется областью влияния.

## Состояния

Для страницы учитывай состояния:

- нормальное состояние с данными;
- загрузка;
- пустое состояние;
- нет результатов после фильтрации;
- ошибка;
- нет доступа;
- частично заполненные или неполные данные;
- длинные названия, тексты и списки.

Если пользователь просит только один статичный макет, все равно проверь, не ломается ли решение при пустом состоянии, длинном контенте и отсутствии результатов.

## Sizing

Выбирай sizing по ожидаемому поведению:

- `Hug` — если размер зависит от содержимого;
- `Fill container` — если элемент должен занимать доступное пространство;
- `Fixed` — если размер должен быть стабильным и это не ломает адаптивность.

Не оставляй `Fixed`, если текст может обрезаться или layout перестает быть устойчивым.

## Использование Компонентов

Страницу собирай из существующих компонентов библиотеки.

Перед созданием нового элемента:

- проверь существующие компоненты и варианты;
- проверь похожие страницы в файле;
- используй уже заданные стили и semantic tokens;
- если нужного компонента или паттерна нет, спроси пользователя.

Не меняй существующие компоненты, варианты, подписи контролов, иконки и порядок элементов без явной задачи.

## Критерии Готовности

Страница готова, если:

- понятна пользовательская задача;
- виден главный сценарий;
- главное действие не спорит со вторичными;
- данные и действия сгруппированы по смыслу;
- внутренние и внешние отступы помогают читать структуру;
- управление расположено рядом с областью влияния;
- использованы существующие компоненты, стили и tokens;
- нет случайных новых паттернов;
- макет можно обсуждать без длинного устного объяснения.

## После Сборки

Перед завершением работы проверь страницу:

- базовая структура соответствует `Main Header` → `Content` → `Page Heading` → `Page Body`;
- ключевые элементы собраны из компонентов библиотеки, а не нарисованы локально;
- локальные визуальные значения не заменяют доступные styles, variables и tokens;
- контейнеры не создают лишнюю вложенность и не превращают каждый блок в карточку;
- действия расположены в зоне, на которую они влияют;
- `Page Body` показывает реальный сценарий, состояние или рабочую сущность страницы;
- названия слоев помогают понять структуру страницы.
