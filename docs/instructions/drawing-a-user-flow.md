# Как рисовать User Flow

Используй этот файл, когда задача связана с созданием, доработкой или ревью user flow.

Отвечай на языке пользователя. Если пользователь пишет на русском, отвечай на русском.

## Цель

User flow нужен, чтобы показать путь пользователя к конкретной цели: от точки входа через шаги и решения к результату.

Это не просто схема экранов. Хороший flow помогает:

- понять, как пользователь реально идет к цели;
- увидеть лишние шаги, тупики, ошибки и пропущенные состояния;
- согласовать логику сценария до UI-деталей и разработки;
- обсуждать happy path и важные альтернативные ветки на одном языке.

## Базовая установка

- Один user flow = одна пользовательская цель.
- Начинай не с экранов, а с задачи пользователя.
- Показывай логику прохождения сценария, а не декоративную композицию.
- Используй общепринятые обозначения, если только пользователь явно не просит другую нотацию.
- Держи схему достаточно простой, чтобы ее можно было понять без устного объяснения.

## Что нужно определить до построения flow

Перед тем как рисовать схему, зафиксируй:

- кто пользователь или сегмент;
- какую именно цель он пытается достичь;
- где пользователь входит в сценарий;
- какой результат считается успешным завершением;
- какие решения, развилки, ограничения и ошибки действительно влияют на прохождение;
- где заканчивается граница этого flow и что остается за рамками.

Если целей несколько, не смешивай их в одну перегруженную схему. Разделяй на отдельные flow.

## Обязательные элементы flow

В каждом user flow должны быть:

- начало;
- конец;
- точка входа в сценарий;
- последовательность шагов пользователя и/или системы;
- decision points там, где путь реально ветвится;
- подписи у переходов, если без них неясно, почему происходит переход;
- happy path;
- важные альтернативные ветки: ошибки, отказы, возвраты, отсутствие данных, повторная попытка.

Если в схеме нет явного начала и явного конца, flow считается незавершенным.

## Общие правила оформления

Используй минимальный и понятный набор фигур.

- `Terminator` или овал/скругленная капсула: начало и конец flow.
- Прямоугольник: экран, шаг, действие, состояние или системный этап.
- Ромб: решение или проверка условия.
- Стрелка: направление движения по сценарию.
- Параллелограмм или отдельная подпись: ввод/вывод данных, если это важно для понимания.
- Выноска/комментарий: только когда без нее команда неправильно поймет логику.

Не придумывай новые фигуры без необходимости. Если нестандартная фигура все же нужна, используй ее последовательно и явно поясни смысл.

## Цвета элементов

- `Terminator` или овал/скругленная капсула: black;
- Прямоугольник: Light pink;
- Ромб: Light blue;
- Стрелка: black;
- У черных `Terminator`-элементов не должно быть видимой обводки. Если у фигуры есть отдельное свойство stroke/border/outline, его нужно отключить или сделать полностью прозрачным.

## Правила логики и структуры

- Начинай flow с entry point, а не с абстрактного "Пользователь".
- Завершай flow конкретным outcome: успех, отказ, ошибка, выход, возврат в список, отправка формы, завершение настройки и так далее.
- Каждый шаг называй через наблюдаемое действие или состояние.
- Для решений формулируй короткий вопрос, а исходящие ветки подписывай ясно: `Да/Нет`, `Есть доступ/Нет доступа`, `Валидно/Невалидно`.
- Если ветка возвращает пользователя назад, показывай это явно.
- Если система выполняет важную проверку или асинхронное действие, не скрывай его.
- Если есть повторяемый цикл, делай его коротким и читаемым, не запутывай схему длинными петлями.
- Не включай редкие edge cases, если они не меняют решение по продукту. Для редких случаев лучше отдельная заметка или отдельный flow.

## Правила композиции

- По умолчанию строй flow слева направо или сверху вниз и не смешивай оба направления без причины.
- Happy path делай самым прямым и визуально доминирующим.
- Альтернативные и error-ветки уводи в сторону, но держи рядом с местом развилки.
- Минимизируй пересечения стрелок.
- Выравнивай элементы по сетке и используй одинаковые отступы между однотипными шагами.
- Сохраняй одинаковый визуальный стиль для одинаковых сущностей по всей схеме.
- Если схема становится слишком большой, разбей ее на несколько связанных flow вместо одного полотна.

## Как подписывать блоки

Подписи должны быть короткими, однозначными и в одном стиле.

- Для действий пользователя используй глагол: `Нажимает "Продолжить"`, `Выбирает объект`, `Подтверждает номер`.
- Для экранов и состояний используй существительное или короткую формулировку состояния: `Экран поиска`, `Пустой результат`, `Ошибка загрузки`.
- Для системных действий используй явную формулировку: `Система проверяет код`, `Сервис создает подборку`.
- Если в подписи используется текст из интерфейса, название раздела, кнопки, фильтра, режима, страницы или другой именованный элемент информационной архитектуры, заворачивай его в кавычки: `Открывает раздел "Набор базы"`, `Нажимает "Позвонить"`.
- Не пиши длинные предложения внутри блоков.
- Не смешивай в одном блоке и действие, и решение, и результат.

## Что обязательно покрывать

Минимум проверь, что в flow отражены:

- основной путь до целевого результата;
- ключевые решения пользователя;
- системные проверки, без которых меняется следующий шаг;
- ошибки валидации или критичные сбои;
- пустые состояния, если они влияют на сценарий;
- возврат назад, повторная попытка или отмена, если это реалистичный путь.

## Порядок работы

1. Сформулируй цель flow в одном предложении.
2. Определи entry point и end state.
3. Выпиши happy path как линейную последовательность шагов.
4. Добавь decision points и важные альтернативные ветки.
5. Проверь, что у каждой ветки есть понятный исход и нет "висящих" блоков.
6. Приведи обозначения, подписи и отступы к единому виду.
7. Упрости: убери все, что не помогает понять сценарий или принять решение.

## Критерии качества

Хороший user flow отвечает на вопросы:

- понятно ли, что хочет сделать пользователь;
- видно ли, откуда начинается сценарий;
- видно ли, чем он заканчивается;
- различимы ли действия, состояния и решения;
- есть ли подписи у неочевидных переходов;
- отражены ли основные ошибки и альтернативы;
- можно ли по схеме обсуждать продуктовую логику без дополнительных объяснений.

## Чего избегать

- нескольких пользовательских целей в одном flow;
- отсутствия начала или конца;
- ромбов без подписанных исходов;
- стрелок без понятного направления;
- перегруженных блоков с длинным текстом;
- смешивания экранов, бизнес-правил и комментариев без визуального различия;
- декоративной сложности вместо логической ясности;
- большого числа второстепенных edge cases, которые ломают читаемость.

## Практическое правило по умолчанию

Если нет специальных указаний, рисуй user flow так:

- один flow на одну цель;
- явный `Start`;
- 5–12 основных блоков на один сценарий;
- один визуально прямой happy path;
- отдельные подписанные ветки для ключевых решений и ошибок;
- явный `End` для каждого логического исхода.

## На чем основаны эти правила

Правила опираются на общие практики UX и flowchart-нотации:

- Figma рекомендует начинать с пользователя и его цели, определять entry point, шаги, decision points и endpoint.
- Miro рекомендует держать один flow сфокусированным на одной цели, не перегружать его и использовать единые символы и подписи.
- Lucidchart и Atlassian рекомендуют использовать стандартные flowchart-символы: terminator для начала/конца, прямоугольник для шага, ромб для решения, стрелки для направления.
