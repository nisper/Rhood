# Режимы выдачи объектов

Этот документ описывает два режима выдачи уникальных объектов:

- таблица
- карта

Документ фиксирует продуктовые правила, смысл колонок, состав данных и поведение интерфейса. Параметры конкретных компонентов, визуальные пропсы и технические детали реализации нужно смотреть в Figma и в коде репозитория.

## Назначение

Выдача помогает СПН быстро оценивать найденные объекты, выбирать приоритетные объявления и переходить к дальнейшим действиям: звонку, просмотру комментариев, добавлению в избранное и ручной работе с дублями.

## Общие правила выдачи

- Пользователь может переключаться между двумя режимами представления: таблица и карта.
- Оба режима показывают один и тот же набор найденных объектов, но делают акцент на разных сценариях работы.
- Состав данных по объекту должен оставаться согласованным между режимами.

## Режим `Таблица`

### Сценарий

Табличный режим нужен для быстрого массового просмотра и обработки объектов, когда пользователю важны сравнение параметров, история контакта и быстрые действия по строке.

### Общие правила таблицы

- Таблица показывает объекты построчно, одна строка на объект.
- Первая колонка всегда содержит чекбокс выбора объекта.
- Для числовых значений используется единый формат `ru-RU`.
- Для дат и времени используется формат `dd.mm.yyyy, hh:mm`.
- Время всегда показывается с ведущим нулем в часах.

### Колонки таблицы

#### `Объект`

- Содержимое всегда двухстрочное.
- Первая строка: краткие характеристики объекта, например `1 ком., 39.2 м², этаж 15/15`.
- Вторая строка: адрес объекта.
- Если адрес длинный, он остается второй строкой и обрезается многоточием.
- Первая строка играет роль основного идентификатора объекта в выдаче.

#### `Покупатель`

- Колонка показывает не количество подходящих заявок, а только факт наличия совпадения.
- Признак совпадения формируется автоматически по результату мэтчинга объекта из парсера с базой покупателей "Этажей".
- Если подходящая заявка есть, пользователь видит специальную отметку о наличии покупателя.
- Если подходящей заявки нет, отметка не показывается.

Причина такого решения: количество подходящих заявок динамическое, а постоянный пересчет счетчика дает слишком большую нагрузку на базу. Поэтому в выдаче хранится только бинарный признак наличия совпадения.

#### `Цена`

- Колонка всегда двухстрочная.
- Первая строка: полная цена объекта.
- Вторая строка: цена за квадратный метр.
- В заголовке колонки также используются две строки:
  - `Цена`
  - `Цена за м²`
- Числовые значения должны читаться как единый числовой блок и выравниваться консистентно.

#### `Позвонить`

- Колонка показывает текущее состояние контакта по объекту.
- Пользователь видит либо доступное действие звонка, либо индикатор того, что по объекту уже звонит конкретный СПН.
- Действие звонка использует подменный номер, который передал агрегатор объявления.
- Если объект уже взят в звонок, интерфейс должен помогать избежать параллельного звонка от другого сотрудника.
- Подробная логика синхронизации звонков и блокировки должна описываться отдельно, когда функционал будет детализирован.

#### `Ликвид.`

- Колонка показывает текущую оценку ликвидности объекта.
- Зафиксированные значения:
  - `Высокая`
  - `Оцениваем`
  - `Средняя`
- До отдельного пересмотра этот блок не меняем.

#### `Источник`

- Колонка всегда двухстрочная.
- Первая строка: агрегатор, например `Авито`, `Циан`, `Яндекс.Недвижимость`, `ДомКлик`.
- Вторая строка: тип автора или конкретное агентство.
- Допустимые базовые варианты второй строки:
  - `Частное лицо`
  - название агентства недвижимости, например `Метрика недвижимости`

#### `Опубликован`

- Показывается одной строкой.
- Формат: `dd.mm.yyyy, hh:mm`.
- Значение должно быть консистентным по всей выдаче.

#### `Статус`

- Это текстовый статус результата звонков.
- Статус нужен, чтобы пользователь видел историю контакта по объекту и мог быстро понять, что уже происходило с объявлением.
- Актуальный набор значений:
  - `Еще не звонили из Rhood`
  - `Последний звонок 15 ч назад`
  - `Последний звонок вчера`
  - `Последний звонок 20.05.2026`
  - `Не отвечает`
  - `Думает`
  - `Отказ`
  - `Другое АН`
- Для статусов, связанных с последним звонком, действует следующая логика:
  - если с момента звонка прошло меньше 24 часов, показываем `Последний звонок N часов назад`
  - если прошло от 24 до 48 часов, показываем `Последний звонок вчера`
  - если прошло больше 48 часов, показываем `Последний звонок dd.mm.yyyy, hh:mm`

Исторический статус `Не выбран` считается устаревшим и больше не используется в актуальной выдаче.

#### `Действия`

- Это отдельная колонка с действиями по объекту.
- Базовые действия:
  - добавить в избранное
  - открыть комментарии
  - открыть меню дополнительных действий
- В дополнительных действиях сейчас ожидаются:
  - `Скопировать код`
  - `Дубль`

`Скопировать код` нужен как быстрый способ передать техподдержке ID объекта в парсере. `Дубль` нужен для ручного связывания найденного объекта с объектом из базы "Этажей".

### Связь с данными

- Для колонки `Покупатель` в выдачу должен попадать не счетчик подходящих заявок, а только признак наличия совпадения.
- Для звонка нужен подменный номер агрегатора и признак, занят ли объект другим СПН.
- Подменный номер нельзя указать в заявке, поэтому прямой номер собственника можно собрать в модальном окне сохранения объекта в CRM.
- Для колонки `Статус` может использоваться дата и время последнего звонка, если звонок был совершен через АТС.

## Режим `На карте`

### Сценарий

Режим карты нужен для пространственного анализа: пользователь смотрит распределение объектов по районам, оценивает близость к интересующим зонам и быстрее принимает решение, какие объекты разбирать в первую очередь.

### Текущий статус описания

- Детальная спецификация режима `На карте` пока не зафиксирована.
- При проектировании карты нужно сохранять смысловую согласованность с табличным режимом.
- Набор данных по объекту и действия по нему не должны противоречить табличной выдаче.

## Карточка объекта

- Карточка объекта должна показывать тот же признак наличия покупателя, что и выдача.
- Для карточки действует та же логика данных: показывается только факт наличия совпадения, без счетчика и без списка заявок.
- Состояние индикатора в карточке не должно расходиться с состоянием колонки `Покупатель` в выдаче.
