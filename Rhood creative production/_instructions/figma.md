# Figma Instructions

Этот файл хранит рабочие правила для правок в Figma по проекту RHOOD.

Сюда складываем не абстрактные принципы, а конкретные договоренности, которые помогают быстрее и стабильнее править макеты.

## Зачем

- не объяснять одни и те же вещи заново;
- фиксировать удачные паттерны работы;
- уменьшать количество повторных ошибок;
- собирать под RHOOD свой способ работы с Figma.

## Маршрутизация

- Для задач с таблицами сначала читай [[docs/patterns/table|table]];
- Для задач с формами и фильтрами сначала читай [[docs/patterns/form.md|форму]];
- Для задач с текстовыми кнопками сначала читай [[_instructions/button.md|button]];
- Для задач с иконками сначала читай [[_instructions/icon.md|icon]];
- Для задач, где нужно добавить или изменить поля, через которые пользователь задаёт или меняет данные, сначала читай [[docs/patterns/form.md|form]].

## Базовые правила

### Сначала переиспользовать

- Сначала ищи готовые компоненты, инстансы и паттерны в текущем файле.
- Если подходящий компонент уже есть, лучше взять его, чем рисовать новый с нуля.
- Если в макете уже существует библиотечная кнопка, строка, ячейка, чип или контрол, по умолчанию используй их.

#### Источники компонентов и иконок

- Для компонентов используй только библиотеку `Parser – Components`.
- Для иконок используй только библиотеку `Parser – Lucide icons`.
- Не используй компоненты, иконки, стили или variables из других подключённых библиотек, даже если там есть подходящий вариант.
- Если в документации компонента указан `source.figma_url`, используй component set по этой ссылке и не ищи альтернативы в подключённых библиотеках.
- Исключение возможно только по прямому указанию пользователя.

### Править точечно

- Если пользователь просит локальную правку, меняй только нужный участок.
- Не перестраивай соседние блоки без необходимости.
- Не меняй геометрию родителя вручную, если layout может сам перестроиться.

### Сначала понять структуру

- Перед правкой смотри, как устроен узел: frame, section, instance, auto-layout.
- Перед удалением или добавлением объектов проверяй родителя.
- Если есть auto-layout, опирайся на него, а не на ручные `x/y`.

#### Ширина контейнеров

- Все контейнеры имеют `Width = Fill container`: они занимают 100% доступного пространства родителя.
- Не задавай контейнеру фиксированную ширину в px, даже если она в текущем состоянии совпадает с шириной родителя.

#### Размеры и отступы

- Для `padding`, `gap`, `border radius`, фиксированных `width` и `height` используй Figma variables из коллекции `sizing`;
- Не оставляй для этих свойств числовые значения в px вручную, кроме `0`;
- Значение `0` оставляй ручным: не назначай для него `base module/0`;
- Сначала ищи подходящую семантическую или компонентную variable. Если её нет, используй `base module`; если не находишь подходящей `variable` спроси пользователя;
- Не создавай `variable` самостоятельно.

### Сначала рабочая версия, потом полировка

- Для первой версии можно делать простой, понятный и функциональный вариант.
- Сначала добиваемся ясной структуры и смысла.
- Потом уже усиливаем визуальную выразительность.

### Не изобретать лишний UI

- Если задачу можно решить существующим паттерном таблицы, модалки, кнопки или списка, не надо придумывать новый паттерн.
- Для внутренних продуктовых сценариев предпочитаем понятный и спокойный UI.

### Названия Figma variables

- Пользователь может передавать названия Figma variables в формате, в котором они копируются из Figma: например, `surface/bg`.
- В обсуждении и при настройке макетов используем этот формат названий без преобразования.

### Названия свойств компонентов

- Для имён `variant properties` и `component properties` источником истины считаем данные Figma Plugin API: `variantProperties` и `componentProperties`.
- Не переносим имена из `get_design_context` без проверки: в сгенерированном коде они могут быть нормализованы, например `padding-x` → `paddingX`.

### Документация Figma variables

- В документах фиксируем назначение variable, место применения и связанные правила композиции;
- Конкретные значения variables в документах не указываем, чтобы не поддерживать несколько источников правды;
- Актуальные значения смотрим в Figma или в соответствующей выгрузке из `docs/variables`.

### Источник variables по умолчанию

- Если задача связана с анализом, проверкой, неймингом, cleanup или обсуждением Figma variables, сначала смотреть выгрузку в папке [[docs/variables|docs/variables]].
- В Figma идти только если в выгрузке не хватает нужного контекста: например, неясны связи с компонентами, `modes`, `aliases` или актуальное состояние после правок.

| Collection        | Purpose                                                                                                                                                               |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `sizing`          | Все про размеры, от базового модуля до настроек компонентов                                                                                                           |
| `palette`         | База цветов. Токены из этой коллекции редко используются в макетах, в основном, они семантических токенов.                                                            |
| `theme`           | Семантические токены, они уже используются в компонентах и макетах. Семантику я выстраиваю от свойства: текст, фон, бордер. Но бывает, приходится идти от компонента. |
| `theme component` | Зачему-то я создал эту коллекцию дли токенов под один компонент.                                                                                                      |
| `inputs variants` | Мои эксперименты с цветом инпутов. Создал коллекцию, чтобы быстро переключать цвет на макете модом, а не держать отдельные версии компонентов.                        |
| `typography`      | Как и с инпутами, только с font-family.                                                                                                                               |

`inputs variants` и `typography` — строго экспериментальные коллекции.

### Роутинг по выгрузке variables

- Нужен цвет для текста, фона, бордера, иконки или состояния компонента — сначала открывай `docs/variables/theme/Value.tokens.json`. Это основной источник семантических variables для макетов.
- Нужно понять, из какого базового цвета состоит семантическая variable или проверить её alias — открывай `docs/variables/palette/Mode 1.tokens.json`. Не начинай с этой коллекции подбор цвета для макета.
- Нужны размеры, отступы, радиусы, размеры компонентов или сетка — открывай один файл из `docs/variables/sizing/` по ширине макета:
  - `1367+.tokens.json` — desktop от 1367 px;
  - `1025–1366.tokens.json` — desktop 1025–1366 px;
  - `768–1024 tablet.tokens.json` — tablet 768–1024 px;
  - `375–767 mobile.tokens.json` — mobile 375–767 px.
- Нужен цвет конкретно для экспериментального состояния input — открывай `docs/variables/inputs variants/` и выбирай mode `bg` или `neutral`.
- Нужна variable для font family — открывай `docs/variables/typography/Roboto.tokens.json`.
- Нужны variables, созданные специально для одного компонента, — открывай `docs/variables/theme component/Mode 1.tokens.json` только для этого компонента.
- Если задача не относится к конкретной категории, не сканируй все файлы: начни с `theme`, а затем переходи в связанную коллекцию только при необходимости.

## Отдельно для компактных меток

- Перед созданием или изменением компактной метки сначала читать [[docs/components/chip.md|chip]] и искать существующий component set `chip`.
- Если метка передаёт выбранное значение или дополнительную информацию, использовать инстанс `chip`, а не собирать `frame` вручную.
- Состав метки настраивать через `component properties`: `thumbnail`, `icon`, `label` и `remove`.
- Включать `remove=true` только когда значение можно удалить.
- Для информационной метки на цветной поверхности по умолчанию проверять вариант `color=contrast`, `style=muted`.

## Проверка перед сдачей

- Использованы существующие instances и component sets, если они подходят для задачи;
- Выбраны корректные variants и component properties;
- Overrides осознанны и не дублируют существующий variant;
- Цвета, размеры, отступы, радиусы и типографика связаны с нужными Figma variables;
- Layout собран через auto-layout, если он применим;
- Контейнеры настроены с `Width = Fill container`;
- У `padding`, `gap`, `border radius` нет ручных числовых значений, кроме `0`: ненулевые значения привязаны к Figma variables;
- Проверено поведение на нужных ширинах и в responsive variants;
- Исключения из правил зафиксированы с причиной.

## Как пополнять базу знаний

Если одно и то же замечание по интерфейсу возникает второй раз, реши, является ли оно общим правилом.

- Для общего правила выбери подходящий документ в `_instructions/` или `docs/` и добавь его туда;
- Формулируй правило через условие и ожидаемое действие;
- Открытые вопросы держи отдельно от утверждённых решений.

## Как дописывать новые правила

Когда появляется полезная договоренность, добавляем ее сюда в одном из форматов:

### Правило

- Когда делаем X, по умолчанию делаем Y.

### Ошибка и вывод

- Ошибка: что пошло не так;
- Как правильно: как надо делать в следующий раз.

### Предпочтение по проекту

- В RHOOD для таких задач предпочитаем такой-то подход.

## Первые зафиксированные наблюдения по RHOOD

- Для простых UI-задач сначала лучше собирать понятную первую версию, а не пытаться сразу делать финальный декоративный вариант;
- При добавлении действий в модалки сначала стоит искать готовые библиотечные кнопки;
- Для задач внутри существующего макета лучше переиспользовать текущие строки, ячейки и компоненты, чем собирать новые вручную;
- Переиспользование компонента считается чистым только если мы не добавляем ему новые визуальные эффекты без явного запроса;
- В ярком цветном баннере для главного CTA по умолчанию используем наиболее заметный вариант `button` с `style=contrast`.
